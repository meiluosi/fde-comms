# 上行模式

高管通常只关心三件事：值多少钱、风险在哪、什么时候看到结果。技术细节、模型选型、架构，讲多了消耗耐心。

## 一页汇报
结论先行，四段：
1. **结论**：一行，项目当前状态和判断。
2. **数字**：不超过三个业务指标，每个写当前值、目标值、口径、测量日期、置信度。没测过就写“待测”，不用估计值冒充。
3. **风险**：当前最大的一个，以及应对。
4. **请对方做什么**：具体到人和时间；写明不决定的代价。

区分“供知悉”和“请决策”，不要把两者混在一段里。细节放附件。用 [一页汇报模板](../templates/one-pager.md)。

## 坏消息
四句话：
1. 发生了什么（事实，不加修饰）；
2. 影响是什么（量化，未知就写未知）；
3. 我们打算怎么办（已经在做的动作）；
4. 需要您做什么（明确请求）。

要点：
- 不拖延。第二周报出的是技术问题，第十周才发现同一个问题就成了信任问题。
- “越早越好”的前提是先核实：已确认的事实、仍未知的部分、下次更新时间，三者都要写。不要因为想快而报没核实的推测。
- 预沟通：重要的坏消息先私下通气，再上会。高管不该在会上第一次听到。
- 不推卸、不过度自责；写事实和动作。
用 [坏消息模板](../templates/bad-news.md)。

## 审稿检查
- 第一行是不是结论；指标是否超过三个、有没有口径和日期。
- 有没有只讲技术不讲业务；有没有没来源的数字；请求是否具体到人和时间。
- 坏消息是否含推测当事实、是否缺“下次更新”。

## 常见失误
把汇报写成工作日志；用技术术语开头；风险列一堆而不是最大一个；请求写成“希望得到支持”。
