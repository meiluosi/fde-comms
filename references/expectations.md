# 预期模式

管的是话术、声明和确认方式，不是 Demo 或试点流程本身：Demo 阶段的事实（范围、已知失败、不做什么）来自 `demo:` 复盘，试点的指标与停止条件来自 `pilot:`，缺了就标“未提供”，不自己补。

## 先判断处在哪个时点
| 时点 | 最容易出的事 | 本模式产出 |
|---|---|---|
| 立项 | 范围膨胀：“顺便把那个也做了” | “本期不做”声明 |
| Demo 前后 | 效果越好，预期越高，Demo 与生产之间隔着落差 | 落差清单与口径（事实来自 demo 复盘） |
| 上线前 | 把合格标准的定义权留给未来某个不高兴的用户 | 验收三问 |
| 变更中 | 要么一口答应，要么一口拒绝 | 变更条目 |
| 运行期 | 预期随时间漂移，错误被当成“系统不行” | 错误画像更新与复盘话术 |

## 一、范围：写“不做什么”
- 立项文档里写明“本期不做”，比“做什么”更需要白纸黑字。能签字最好；拿不到签字，就用会议纪要或邮件请对方回复确认，并留存。
- 范围外的请求按变更处理：写下它是什么、影响哪些交付与期限、替代做法、代价，请对方选择。不要一口答应，也不要一口回绝。
- 事实输入：`framing:` 定义卡的“本期不做”，`demo:` 复盘的失败样例。

## 二、能力讲解：先错误画像，再比喻
- 比喻只用来开场，并且要准确，否则造成更深的误解。“读得很多但没有记性的实习生”“很自信的翻译”可以解释知识面广、会编造，但不要用它暗示系统会像人一样成长，也不要把“只会补全句子”当作完整描述。
- 更有效的是在客户自己的数据上给出错误画像：会错成什么样、大概多常发生、人能不能一眼看出来、出错时谁兜底。没有测过就写“待测”，不套用行业平均。
- 纪律：不说“这个AI做不到”，说“这个做法的风险在……，建议的替代路径是……”，并带上代价。确实不可行时直接说“不建议”，不用委婉掩盖。

## 三、Demo 前后：落差清单
- Demo 前先说清：这次演示了什么、没演示什么、用的数据是否真实。
- Demo 后列出到生产还差什么：数据与权限、手写等已知失败类型、集成、人工确认环节。事实来自 `demo:` 复盘（如 `demo:L3`），不由本 Skill 判断 Demo 成败。
- 客户说“效果这么好，下个月全量上线”时：感谢并复述其期望，再给出落差清单与最近一个可检验的下一步（通常是试点），不当场承诺时间。

## 四、上线前：验收三问
必须和客户共同确认，缺一不可：
1. 多高的准确率算合格？（口径、样本、谁来评判；数字由客户确认，不套行业平均）
2. 哪类错误绝对不能接受？
3. 出错时谁兜底？（责任归属与人工确认环节，不是把系统输出换个名字叫“建议”就算完成）

## 五、让业务方真正参与
- 共同定义指标：拉业务负责人一起定，也能提前暴露双方对“成功”的理解差异。
- 轮值试用：业务团队排班轮流用，每人写几句反馈，避免变成“他们几个人的项目”。
- 一线标注小组：评测集最需要业务知识。让资深员工参与并给予正式认可。
- 注意：若有人担心被替代，先说清岗位影响，再邀请其建设评测集；否则等于让人训练自己的替代者。

## 审稿检查
- 有没有“本期不做”和确认方式；是否只写了范围内的事。
- 验收三问是否齐全，数字是否由客户确认；兜底是否具体到岗位。
- 能力说明是否有错误画像，而不只有比喻；有没有“做不到”而缺代价与替代。
- Demo 落差清单的事实是否有来源；有没有替用户承诺时间或效果。
